## 1. 공통 실행 기록 — T-020

한 실행 기록에는 아래 항목을 남긴다. 미실행 항목은 `null` 또는 `not_run`으로 유지하고 예시 숫자로 채우지 않는다.

| 항목 | 기록 규칙 |
|---|---|
| 식별 | run_id, 연결 T/FR/DEC, 입력 ID와 입력 파일 SHA-256, 구성 ID·해시, 실험 코드 해시 |
| 후보 구성 | 알고리즘·패키지 버전/커밋, 모델/체크포인트 해시, 라이선스 근거, 변형·보간·경계 모드 |
| 실행 환경 | 환경 ID, 장비 JSON과 그 해시, OS·드라이버·사용 GPU, 카메라 모드·마이크 모드·대상 앱 버전 |
| 재현 단계 | 순서대로 실행할 명령·사용자 행동, 입력값, 정상·오류·취소 조건, 예상 결과 |
| 실제 결과 | 실행 시작/종료 시각, 처리 단계별 결과, 반복별 측정값, 결과 파일·로그·동의한 관찰 근거 |
| 평가 | 아래 품질 항목별 점수·문제 부위·재현 동작, 수정량, 시간·프레임·지연·자원 |
| 결론 | 통과/일부 실패/실패/미실행, 지원/제외/미정, 제한·원인, 재검증 T 번호, 기록자 |

실험을 시작하기 전에 입력·후보 버전·환경·단계·예상 결과를 채운다. 실험 중 파라미터를 바꾸면 기존 결과를 덮지 않고 새 run_id로 기록한다. 입력 원본·정상 결과는 보존한다. 생성 이미지는 저장 파일 해시가 원본이며 같은 프롬프트 재생성을 동일 입력으로 간주하지 않는다.

## 2. 품질 평가 척도 — T-019

각 항목은 **3점이 가장 좋고 0점이 가장 나쁘다**. 단일 평균만으로 결함을 숨기지 않고 부위·동작·심각도를 함께 기록한다. 판정이 불가능하면 `미평가`로 두며 0점과 구분한다. 출시 합격 점수·표본은 DEC-11/T-047에서 결정한다.

| 항목 | 3점 | 2점 | 1점 | 0점 |
|---|---|---|---|---|
| 원화 인상 | 얼굴 비율·색·선·표정 인상이 유지됨 | 국소 변화가 있으나 인상 유지 | 얼굴/눈/입 비율이나 선·색이 눈에 띄게 달라짐 | 다른 캐릭터처럼 보이거나 주요 얼굴 훼손 |
| 경계·겹침 | 신규 틈·테두리·순서 오류가 보이지 않음 | 특정 극단 동작에서만 작은 결함 | 중립·자주 쓰는 동작에서 틈·겹침·색 번짐 | 주요 부위 소실·큰 구멍·광범위 잘못된 합성 |
| 눈 움직임 | 열린/중립/감은 상태·좌우·복합 동작이 일관됨 | 일부 극단에서 국소 찌그러짐 | 깜빡임 중 눈동자·선·좌우가 자주 어긋남 | 눈 동작 불가·잘못된 부위가 움직임 |
| 입 움직임 | 닫힘·열림과 입력 반응이 일관되고 원화 인상 유지 | 일부 범위의 작은 결함 | 닫힌 입이 새거나 빈번한 찢어짐·부자연스러운 벌어짐 | 입 동작 불가·다른 부위 움직임·주요 얼굴 훼손 |
| 고개 움직임 | 공표할 제한 범위에서 인상·겹침·연결 유지 | 범위 끝의 작은 결함 | 일반 범위에서도 부위가 미끄러지거나 뻣뻣한 단절 | 구조 붕괴·얼굴 분리·지원 동작 불가 |

각 시료는 `원본 → 자동 결과 중립 → 눈/입 최소·최대 → 고개 제한 끝 → 복합 동작 → 보정 후 같은 상태`로 비교한다. 고개는 후보별 정규화 값 -1/0/+1과 실제 각도·단위를 같이 적는다. 이를 완전한 측면·후면 복원 성공으로 해석하지 않는다.

고급 이미지 요구는 `NFR-ART-01`로 연결한다. HQ-001에서 눈동자·속눈썹·잔머리·얇은 선·금속/자수·원단 명암을 원본 크기 100%와 실제 출력 크기로 각각 비교한다. 확대·축소 배율과 출력 해상도를 적고, 원화의 세부 묘사를 단순한 색면으로 바꾸어 품질 문제를 숨기지 않는다. 고해상도 파일이라는 이유만으로 고급 품질로 판정하지 않는다.

HQ-002는 입력 자체의 경계 결함을 먼저 표시한다. 알고리즘이 새로 만든 결함과 원본 결함을 구분하며, 원본 결함이 그대로 남았다는 이유만으로 ‘새 경계 오류 없음=깨끗한 투명 출력’으로 기록하지 않는다. 깨끗한 알파 품질은 별도의 정상 입력에서도 확인해야 한다.

## 3. 보정 부담과 사람의 개입

| 측정 | 정의 |
|---|---|
| 보정 부위 수 | 수정한 고유 부위 ID 수. 같은 눈을 여러 번 고쳐도 부위 수는 1 |
| 보정 행동 수 | 위치·영역·역할·순서·범위의 의미 있는 적용 횟수. 연속 드래그는 1회, 되돌리기·재수정은 별도 |
| 능동 작업 시간 | 입력 선택·문제 이해·수정·검색·해결 시간. 처리 대기와 겹치면 능동 시간으로 우선 분류 |
| 대기 / 재분석 | 처리 대기 합계와 재분석 횟수, 실패·포기·시간 제한 이유 |
| 도움 | 없음 / 일반 안내 / 과제별 힌트 / 대리 조작. 개발자 리허설과 실제 초보자 결과 분리 |
| 원본 손상 | 원본·마지막 정상 저장본의 손상 또는 프로젝트 간 결과 혼입은 품질 평균과 무관하게 중대한 실패로 기록 |

도구 제작자가 fixtures를 검사한 기록은 초보 사용자가 완주한 증거가 아니다. 신규 사용자 조사는 01 조사 계획을 따르고 실제 제품 관찰은 T-281~284와 연결한다.

## 4. 성능·시간 기록 기준

| 항목 | 측정 구간·필수 기록 |
|---|---|
| 읽기·분석·분리·보완·변환 시간 | 각 단계의 시작→결과 준비까지 벽시계 시간. 파일 I/O·모델 로딩·모델 추론·GPU 동기화 포함/제외 명시. 전체 사용자 대기 시간도 별도 기록 |
| 반복 | 파일 처리 탐색 실험은 워밍업 1회 후 같은 입력·구성으로 측정 3회를 기본값으로 사용. 첫 로드 시간도 별도 보존. 오류·이상치를 버리지 않음 |
| 프레임 | 실제 프레임 타임스탬프/길이 원자료. 평균 FPS와 p50/p95/p99·최대 프레임 시간·끊김. 탐색 연속 구간은 최소 30초×3회를 계획하고 실제 시간·표본 수 명시 |
| 입력→앱 / 앱→방송 / 입력→방송 지연 | 측정 구간을 반드시 구분. 같은 단조 시계로 비교 가능하면 타임스탬프 사용. 외부 수신 시각을 얻을 수 없으면 동의한 고속 촬영 등 관찰 방법·시간 해상도·추정 오차를 기록. 앱 내부 시간만으로 방송 지연을 주장하지 않음 |
| 자원 | 측정 도구·샘플 간격, 프로세스 CPU·작업 메모리·GPU/VRAM·시스템 동시 부하. GPU 선택·전원/발열 상태·출력 크기·캐릭터 복잡도·방송 장면 기록 |
| 연속 실행 | 입력·장치·장면·동시 앱·확정 시간을 기록. 준비 검사의 몇 초 실행으로 2시간 방송 동시 안정성을 통과시키지 않음 |

현재 30 FPS·지연 p95 200ms·연속 2시간·첫 움직임 10분·방송 20분은 PRD의 초기 제안이다. 이 양식의 탐색 반복 수나 세션 길이가 출시 검증 표본·임계값을 확정하지 않는다. 실제 기준은 T-047에서 결정한다. `preflight_wall_ms`는 준비 도구의 파일 검사 시간이며 분석 추론·실시간 렌더·추적 지연이 아니다.

## 5. 준비 검사 재현 순서

1. [실행 안내](../../experiments/phase02/README.md)에 따라 Python 환경을 생성하고 잠금 파일의 휠 해시로 설치한다. 시스템 패키지 공유는 사용하지 않는다.
2. 환경 수집기를 실행하고 ENV-WIN-001 JSON과 해시를 실행 기록에 연결한다. 다른 PC는 새 환경 ID로 기록한다.
3. manifest에서 입력 ID·출처·허용 목적·해시를 확인한다. 고급 원화 PNG는 저장 파일 그대로 보존한다.
4. `lab.py build`로 절차 fixtures·구조·미리보기를 재생성한다. 기존 생성 원본과 비교할 때 구성·코드·Pillow 버전을 맞춘다.
5. `lab.py verify`를 실행한다. 29개 입력의 예상 오류·경고, 50개 파일 해시, 정상/잘린 좌표 표현의 등가성 확인이 기대 결과다.
6. `lab.py new-run --input HQ-001 --id ...`로 후속 실험 양식을 만든다. 입력·구성 해시가 자동 연결되며 상태는 `not_run`이다. 위 필수 실행 조건을 채운 뒤 실제 과제를 실행한다.
7. 실제 결과·근거·실패·제한·재검증을 기록하고, 검사 통과와 제품의 기능·품질 통과를 구분한다.

실제 준비 결과는 [readiness-001.json](../../experiments/phase02/results/readiness-001.json), 재생성 결과는 [reproducibility-001.json](../../experiments/phase02/results/reproducibility-001.json)에서 확인한다. 의도한 오류를 올바르게 탐지한 사례도 준비 검사 통과에 포함되므로 ‘29건 모두 캐릭터 변환 성공’으로 읽지 않는다.
