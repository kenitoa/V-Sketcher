## 1. 판정 단위와 재현 조건

각 결과는 빌드/설정 hash, OS 빌드·GPU/장치 드라이버, 모델/셰이더/scene/자산 hash, 입력 경로·원본·리비전, 실제 출력 해상도·복잡도, OBS/외부 대상 버전, 전원/성능 설정, 반복 번호와 증거를 기록한다. 측정 도중 설정·조건을 바꾸면 별도 run이다. 개발자 리허설·사용자 대리 조작·실제 사용자 결과를 섞지 않는다.

기준 PC는 DEC-01의 i5-13420H·32GB급·RTX 4050 Laptop·Windows 11 x64다. 전원 연결·성능 모드·원격 세션 아님·GPU 실제 backend를 기록하고, 작업과 무관한 고부하 앱을 닫는다. 시스템 전체 CPU와 앱 프로세스 트리의 CPU를 따로 수집한다. 장치·드라이버가 달라지면 같은 성능 등급으로 합치지 않는다.

기본 장면은 1캐릭터, 1920×1080 투명 출력, 원본 고급 아트 최대 4096px·16MP, 최대 64부위 계약이다. 내부 기본 조합의 대표 10개·정면 한 장 10개·분리 묶음 10개를 성능/정상 입력 기술 집합으로 마련한다. 각 경로 최소 6개는 얼굴·가닥·의상 세부가 있는 고급 아트다. 무권한 원본·원본 경로에 묶인 자료는 사용하지 않는다. 03~04의 512px 도형 및 고급 샘플 몇 장이 이 새 집합을 채웠다고 세지 않는다.

## 2. 프레임·지연·자원 계약

| ID | 확정된 통과 기준 | 측정 방식 / 표본 |
|---|---|---|
| PERF-01 GPU 렌더 능력 | 1080p에서 **실제 완료 렌더 ≥30FPS**, p95 렌더 작업 ≤33.3ms | 30 제한을 풀어 GPU 완료까지의 시간을 측정하는 능력 시험과 고정 30Hz 실행을 분리. rAF 호출·OBS 인코더 프레임만 세지 않음 |
| PERF-02 실제 30Hz 전달 | 30FPS 설정, source의 실제 새 완료 frame sequence 누락 ≤1%, 100ms 초과 끊김 0회/60초 | 고정 30Hz 예상 frame count와 실제 source 완료 ID·OBS 수신을 대조. 29.7 등의 원래 FPS는 그대로 보고하고 30으로 올려 쓰지 않음. 정지 포즈라도 새 렌더는 셀 수 있지만 이전 캔버스 복제/인코더 반복은 source 새 프레임이 아님 |
| PERF-03 소프트웨어 지연 | 실제 카메라 프레임 획득 완료→새 제어를 반영한 OBS source draw 완료 ACK **p95 ≤200ms** | 동일 monotonic 기준으로 worker/main/browser 타임스탬프를 보정. GPU 완료·frame ID와 연결. 센서 노출·화면 scanout·네트워크 인코딩 지연 제외를 명시. 캡처/추론/IPC/렌더/소스 소비를 분해 보고 |
| PERF-04 실제 체감 지연 | 실제 움직임/동기 기준 표식→OBS 화면 변화 **p95 ≤200ms** | 120FPS 이상 동기 촬영 등 독립 계측으로 최소 30개 반응 사건×3회. 장비/표식/반응 판정 규칙 사전 고정. PERF-03 또는 PNG 발행 ACK를 이 측정으로 대체하지 않음 |
| PERF-05 자원 | 앱+worker 프로세스 트리 RSS 합 ≤2GiB, OBS RSS ≤1GiB, 앱 트리 CPU p95 ≤논리 코어 전체의 30% | 1초 표본. RSS 합에는 공유 페이지 중복이 있음을 표시. CPU는 1코어=100% 값을 논리 코어 수로 나눈 정규화와 원자료를 모두 보존 |
| PERF-06 GPU 예산 | 앱의 resident 텍스처·버퍼 계산 예산 ≤512MiB | 해상도·상태·mipmap·버퍼 할당으로 추적하고 실제 GPU/adapter 수치도 가능한 범위에서 기록. 시스템 전체 GPU 값을 앱 전용 사용량으로 표기하지 않음 |
| PERF-07 초기 분석/상호작용 | 지원 입력의 분석 p95 ≤30초, 취소 UI 반응 ≤200ms, 파일/분석 작업 중 실행 제어 유지 | 경로별 입력 10개×3회, cold/warm 분리. 디코드/준비/모델 시간을 분리. 전체 사용자 작업 시간과 자동 대기 구간을 섞지 않음 |

M0 재검증은 경로당 대표 고급 장면 1개×3회, 워밍업 10초 뒤 60초씩 같은 입력 재생으로 렌더/출력을 비교한다. 실제 카메라·기본 마이크·OBS x264 기록이 함께 실행되는 60초×3회도 별도로 실시한다. 기록된 제어 재생은 새 라이브 추적 성공으로 세지 않는다. **현재 14.08FPS는 640px CPU/PNG 시험의 실패 근거**이며 새 1080p GPU 경로는 NOT_RUN이다.

출시 성능은 정상 기술 집합 30개×3회, 각 10초 워밍업+60초, 앱 미리보기+OBS Browser Source+1280×720/30FPS x264 로컬 녹화를 기본 부하로 고정한다. 한 경로의 실패를 다른 경로 평균으로 상쇄하지 않는다. 해상도·복잡도 최대 한도는 별도 최대 입력 스트레스 집합에서 확인한다. 평균만 통과해 p95·끊김·목표 복잡도를 실패하면 보류다.

## 5. 초보자·시간·표본

[01의 분모·관찰창·실패/도움 규칙](./01-metrics.md)을 유지하고 다음 목표를 확정한다. 미완료/포기/시간 제한을 성공 시간 0초나 최대 시간의 성공으로 바꾸지 않는다. 성공자 시간 중앙값만 제시하지 않고 성공률·실패자 경과 시간도 함께 보고한다.

| UX-05 보정 부담 | 경로별 보정 행동 중앙값 ≤3회, p90 ≤8회, 대리 조작 없는 성공. 재분석 뒤 최초 보정 부담을 지우지 않음 |
| UX-06 반복 | 최초 정상 저장 뒤 14일 관찰창에서 재열기/재사용 ≥6/10/경로, 프로젝트/외부 결과의 독립성·누락을 기록. 관찰 중인 사람을 성공으로 미리 세지 않음 |

UR-001은 리깅 복잡성에 대한 실제 경험과 장치 입력 참여 근거다. 위 최초 초보자 제품 완주 30명이나 ART 평가자 3명의 대체물이 아니다. 현재 UX-M0 및 출시 표본은 **0명 / NOT_RUN**이다. 기간·모집·비용을 이미 확보했다고 가정하지 않는다. 일정은 이 표본/계측 자원이 마련된 뒤 잡는다.

## 6. 통과·보류와 재검토

판정은 `PASS / FAIL / PARTIAL / NOT_RUN / BLOCKED`로 남긴다. PARTIAL·NOT_RUN·BLOCKED는 PASS가 아니다. M0에는 기술/표현/외부 독립 활용의 치명적 위험을 확인하는 최소 검증을 요구하고, 출시에는 위 전체 조건과 PRD 필수 수용 기준을 요구한다. M0 통과가 출시 통과를 의미하지 않는다.

실패는 M0-R ID·원인·책임·실험 조건·재현/성공 증거에 연결한다. 같은 조건의 반복 성공 뒤에만 상태를 바꾼다. 새 알고리즘/스키마/의존/외부 버전·GPU/장치·지원 한도·품질 기준 변경은 해당 게이트를 다시 연다. 기존 03/04의 측정 완료 체크를 취소하지 않고 **후속 재검증 상태**를 추가해 역사와 현재 판정을 함께 보존한다.
