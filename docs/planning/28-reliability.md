## 데이터 보호와 복구의 실제 시험

`tools/reliability-child.cjs`는 테스트 소유 프로세스에서 실제 제품 코드를 실행한다. 저장의 쓰기 전·fsync 후·검증 후·백업 전/후·교체 전/후에서 준비 신호를 보낸 후 부모가 해당 PID만 강제 종료한다. 교체 전에는 기존 정상본 해시, 교체 후에는 새 정상본 해시를 확인하고, 가능한 백업도 다시 읽는다. stale writer lock 회수 뒤 재시도하여 정상 파일을 재검증한다.

편집은 정상 파일을 연 뒤 수정·영속 복구본을 만들고 프로세스를 종료한다. 다음 ProjectSession에서 실제 복구본을 발견·복원해 새 파일로 저장하며 기존 정상 파일 해시가 변하지 않아야 한다. 저장된 복구본 이후의 모든 키 입력이 보존된다고 약속하지 않는다.

INP는 이전 정상 출력물을 안전 저장 API의 입력으로 사용해 쓰기/동기화/교체 경계에서 종료·재시도한다. 이 시험은 새 외부 호환/독립 구동 검증을 뜻하지 않는다. 분석은 실제 Python worker 시작 중 종료 후 실제 분석 어댑터로 다시 실행한다. 사용자 원본이 아니라 권한 있는 고급 샘플을 사용한다.

시험 파일·캐시·미완료 tmp·프로세스별 lock은 무시되는 `.local/reliability-*` 아래에 둔다. 정상 사용자 프로젝트를 조작하지 않는다. 비정상 종료로 남은 tmp를 유효 복구본으로 제공하지 않으며, tmp 자동 정리의 전 범위 승인을 별도로 주장하지 않는다.

## 개인정보와 고지 누락 보완

호스트 회귀에서는 프로젝트 이름·개인 경로·비밀값·영상/PCM을 대신하는 canary를 의도적으로 넣고 정상 로그·진단·방송 상태에서 빠지는지 검사한다. 방송 상태는 원래 허용된 제어 필드만 받으며 추가 영상/음성 필드는 거부해야 한다. 로그의 허용 필드라도 원시 오류 문자열이면 저장하지 않아야 한다.

고지 검사에서 FlatBuffers 25.12.19 설치 wheel에 복사할 라이선스 원문이 없음을 확인했다. [해당 공식 버전의 원문](https://raw.githubusercontent.com/google/flatbuffers/v25.12.19/LICENSE)을 `worker/resources/third-party/flatbuffers/LICENSE`에 보관하고 출처·버전·SHA-256을 `worker/resources/license-overrides.json`으로 고정했다. `scripts/notices.py`는 버전과 해시를 확인해 고지에 복사한다. 다른 버전으로 의존성이 바뀌면 조용히 같은 원문을 재사용하지 않고 실패한다.

Node의 중첩 의존성은 루트 `node_modules` 이름만으로 버전을 판정하지 않는다. 정확한 잠금 파일 경로/버전과 원문을 대조한다. 기존 아트·원본·실험·과거 evidence는 수정하지 않는다. 고지 복사 변경 때문에 새 포터블 제작과 실제 패키지 self-check를 수행한다. 게시·push·서명·배포는 하지 않는다.

## 남은 출시 차단 조건

- 실제 앱의 정상 얼굴 검출·중립 보정과 라이브 음성/물리 장치 복구가 미확인이다.
- 세 경로 각각 2시간의 실제 장치·OBS 녹화 동시 시험과 메모리/CPU/GPU/온도 추세가 없다.
- PERF-03 실제 카메라 프레임→OBS 완료 계측과 PERF-04 독립 촬영 지연 계측이 없다.
- 기준 입력 30개·3반복과 최대 해상도/복잡도·동시 작업 부하, 독립 아트/초보자 관찰, 깨끗한 Windows는 아직 별도 게이트다.
- 실제 가득 찬 격리 파일시스템의 저장 실패는 controlled ENOSPC와 구분해 추가해야 한다.

따라서 28 종료와 M0/출시 승인을 선언하지 않는다. 개별 검증 결과는 PASS/PARTIAL/NOT_RUN/BLOCKED로 구분한다.

1080p/30Hz 설정의 짧은 무부하 완료 FPS는 **29.998250101958185**, draw+`gl.finish` 벽시계 p95는 **0.8000000715255737ms**였다. 8ms 추가 CPU 부하 조건은 **29.998500075234645FPS**, 벽시계 p95 **8.700000047683716ms**였다. 실제 측정값을 30FPS로 올려 쓰지 않는다. 이 값은 센서·worker·IPC·OBS 지연이 아니며, GPU-only timestamp나 측정 컨텍스트의 GPU 어댑터 식별을 대신하지 않는다. 기준 전원 모드·전체 부하 조건을 고정한 출시 벤치마크도 아니다. [환경](../../evidence/phase28/run-02/environment.json)에 그 한계를 기록했다.

재현은 `.local\toolchain\node-v24.22.3-win-x64\node.exe scripts/verify-reliability.mjs evidence/phase28/<새 실행 이름>`이다. 기존 결과 폴더는 거부한다. 필수 gate→실제 저장/종료→반복/개인정보→공통 WebGL→고지→로컬 포터블 제작→패키지 self-check 2회→ZIP 고지 검사를 실행한다. 이후 `.venv-product\Scripts\python.exe scripts/reliability-review.py --run=evidence/phase28/<그 실행 이름>`으로 결과·소스 해시·위험·완료 범위를 고정한다.

개발 중 GPU 시험은 폐기한 renderer에 다시 draw하는 잘못된 검사와, 재사용할 canvas의 컨텍스트를 먼저 상실시키는 검사 오류를 수정했다. 실패 파일은 run-01 아래에 보존했고, 올바른 해제 추정값과 활성 컨텍스트로 run-02에서 다시 검증했다. 제품의 렌더/저장 방식을 바꾸거나 보안 설정을 완화해 통과시킨 것이 아니다.

공개 전송·서명·push·게시를 수행하지 않았다. 이번 범위의 제품 런타임 로직 변경은 없으며, 실제 보완은 정확 버전 라이선스 원문과 빌드 고지 복사다.
