# 2DSketcher 제품 요구사항 정의서 (PRD)

> 그림 도구를 모르는 사람도 자신의 버추얼 캐릭터를 만들고, 움직임을 연결해 실제 방송에서 사용할 수 있게 한다.

| 항목 | 내용 |
|---|---|
| 프로젝트 | 2DSketcher |
| 문서 버전 | v0.14 — 13단계 파츠 자산·조합 제작 반영 |
| 작성일 | 2026-11-16 |
| 최종 갱신 | 2026-11-17 |
| 문서 상태 | 01~13 작업 완료. 모델 1.3·새 고급 파츠 64조합/조절/연동/매핑·공통 입력/편집/움직임/보존 구현. M0 HOLD·재검증 5건, 한 장/분리 자동 제작·추적/방송/전체 변환·독립 품질 평가는 후속 |
| 초기 제품 중심 | 2D 버추얼 캐릭터 제작, 실시간 실행, 방송 연결, 외부 내보내기 |
| 필수 장기 확장 | 그림 기반 3D 캐릭터 제작, 자체 모델을 이용한 글 기반 캐릭터 생성 |
| 최종 성공 기준 | 캐릭터가 편집기 안에서 움직이는 것을 넘어, 사용자가 실제 방송에서 사용할 수 있음 |

## 1. 문서의 목적과 해석 기준

이 문서는 제품의 목적, 사용자 경험, 기능 범위, 품질 기준, 개발 순서와 검증 과제를 정의한다. 특정 프레임워크, 그래픽 엔진, 모델 구조를 확정하는 기술 설계서는 아니다. 후속 설계에서는 이 문서의 요구사항 ID를 기능 명세, 작업 항목, 테스트와 연결한다.

요구사항의 상태는 다음과 같이 구분한다.

- **확정 방향**: 사용자와의 대화에서 명시적으로 합의한 제품 요구사항이다.
- **설계 제안**: 확정 방향을 실제 사용자 경험으로 만들기 위한 초안이다. 구현 검증과 후속 논의를 통해 조정할 수 있다.
- **미정 / 검증 필요**: 대상 환경, 호환 형식, 수치, 기술 방식 등을 아직 결정하지 않았다. 현재 지원되는 기능이나 성능으로 해석하지 않는다.

이 문서에서 “해야 한다”는 구현 완료를 의미하지 않는다. 제품이 충족해야 할 요구사항을 뜻한다. 아래의 세부 화면, 자동화 방식, 수용 기준과 단계 구분은 별도 표기가 없으면 **설계 제안**이다. 2절의 확정 방향을 축소하거나 대체하는 근거로 사용하지 않는다.

05단계의 [DEC-01~12](./planning/05-decisions.md)와 [선정 스택](./planning/05-stack.md), [판정 계약 v1.0](./planning/05-release-gates.md)은 **초기 구현 기준으로 채택한 결정**이다. 채택과 제품 구현·출시 지원 검증은 구분한다. 같은 항목의 이전 ‘미정/제안’ 기록은 05의 결정으로 갱신하되 원래 실험 결과를 소급해 합격으로 바꾸지 않는다. [M0는 HOLD](./planning/05-m0-review.md)이며 후속 기술 검증이 필요하다.

## 2. 확정된 제품 방향

| ID | 확정 방향 | 기획에 미치는 영향 |
|---|---|---|
| PD-01 | 주요 사용자는 그림 프로그램과 제작 도구를 전혀 모를 수 있다. | 전문 용어 학습이나 수작업 리깅을 시작 조건으로 요구하지 않는다. |
| PD-02 | 캐릭터 이미지, 반응하는 캐릭터, 움직이는 버추얼 아바타가 모두 중요하다. | 이미지 제작부터 반응 설정, 추적 연결까지 하나의 작업으로 이어져야 한다. |
| PD-03 | 준비된 파츠를 조합해 캐릭터를 만들 수 있어야 한다. | 파츠 라이브러리와 조합·색상·형태 편집이 필요하다. |
| PD-04 | 한 장짜리 그림을 가져와도 프로그램이 최대한 알아서 움직이게 해야 한다. | 그림 분석, 자동 움직임 준비, 미리보기와 쉬운 보정이 핵심이다. |
| PD-05 | 부위가 나뉜 그림을 가져와 안내에 따라 설정할 수 있어야 한다. | 분리된 부위의 역할 인식과 초보자용 연결 안내가 필요하다. |
| PD-06 | 글로 설명해서 캐릭터를 생성하는 방식도 필요하다. | 전체 제품 범위에 포함하되, 구체적인 설계는 추후 진행한다. |
| PD-07 | 글 기반 생성은 자체 모델을 제작하고 연결하는 방향이다. | 외부 이미지 생성 API를 호출하는 구조를 이 기능의 최종 방향으로 두지 않는다. |
| PD-08 | 초기에는 2D 캐릭터에 집중한다. | 초기 제작·편집·실행·내보내기의 기준은 2D다. |
| PD-09 | 그림을 바탕으로 입체적인 3D 캐릭터를 만드는 기능도 필요하다. | 선택적 아이디어가 아니라 필수 장기 확장으로 관리한다. |
| PD-10 | 만든 캐릭터를 우리 프로그램에서 계속 실행하며 방송에 연결할 수 있어야 한다. | 제작 도구뿐 아니라 실시간 아바타 실행기와 방송 출력 기능이 필요하다. |
| PD-11 | 만든 캐릭터를 외부 프로그램용으로 내보낼 수 있어야 한다. | 프로젝트 저장과 구분되는 외부 호환 내보내기가 필요하다. |
| PD-12 | 최종 가치는 캐릭터의 실제 사용 가능성이다. | 실제 방송 연결 및 외부 프로그램 구동 검증을 완료 기준에 포함한다. |

**핵심 범위 원칙:** 앱 내 실행과 외부 내보내기는 모두 필수다. 둘 중 하나를 다른 하나의 대체 기능으로 취급하지 않는다. 3D와 자체 모델 생성의 개발 시점은 뒤로 둘 수 있지만 전체 제품 요구사항에서 제외하지 않는다.

## 3. 해결하려는 문제

### 3.1 사용자 문제 가설

다음 항목은 기획의 출발점이며, 사용자 조사로 검증해야 한다.

1. 캐릭터를 갖고 싶어도 그림 도구, 레이어, 메시, 리깅 등을 몰라 제작을 시작하지 못한다.
2. 마음에 드는 그림 한 장은 있지만 움직일 수 있는 캐릭터로 바꾸는 방법을 모른다.
3. 외형 제작, 움직임 설정, 추적, 방송 연결을 각각 다른 도구에서 해야 하면 중간에 포기한다.
4. 자동화 결과가 어색할 때 무엇을 어떻게 고쳐야 하는지 알 수 없다.
5. 완성한 캐릭터가 특정 도구 안에서만 보이거나 방송에 연결되지 않으면 실제 활용 가치가 낮다.
6. 사용 경험이 쌓이면 자동 결과를 더 정교하게 수정하고 외부 프로그램에서도 사용하고 싶어진다.

### 3.2 제품이 제공할 가치

- **쉽게 시작하기:** 파츠를 고르거나 그림을 가져오는 것으로 제작을 시작한다.
- **빠르게 반응 확인하기:** 복잡한 편집 전에 캐릭터가 눈을 깜빡이거나 입을 움직이는 결과를 본다.
- **안내에 따라 완성하기:** 자동 처리가 부족한 부분만 이해하기 쉬운 행동으로 보정한다.
- **실제로 사용하기:** 앱에서 실행해 방송에 연결하거나 지원하는 외부 프로그램으로 내보낸다.
- **계속 발전시키기:** 원본 프로젝트를 보존하고 외형, 표정, 움직임을 반복 수정한다.

### 3.3 최초 실제 경험 확인 — 2026-11-16

[UR-001](./planning/01-user-research.md#ur-001)에서 프로젝트 사용자는 AI 버튜버 시스템 구현 경험 중 리깅이 매우 복잡했다고 보고했다. 사용 환경은 Windows PC·웹캠·헤드셋 마이크·OBS Studio였다. 파츠·한 장 그림·분리 그림의 세 경로와 앱 내 실행·외부 활용 모두가 필요하다는 제품 방향도 재확인했다.

이는 구현 경험자 1명의 자기보고다. 초보자 직접 관찰이나 방송 연결 성공·성능 검증 결과가 아니다. 파일 형식·장비 사양·OS 및 도구 버전·세부 작업 순서는 미확인이다. Windows와 OBS Studio를 초기 검증 우선 후보로 삼되 지원 확정으로 해석하지 않는다. 초보자의 실제 완주 가능성은 [최초 조사 계획](./planning/01-user-research.md)에 따라 후속 관찰한다.

## 4. 대상 사용자와 대표 상황

| 사용자 | 현재 상태 | 원하는 결과 | 제품이 줄여야 할 부담 |
|---|---|---|---|
| 입문자 | 그림 도구와 버추얼 캐릭터 제작 경험이 없음 | 자신을 표현하는 캐릭터로 방송 시작 | 전문 용어, 설치·연결 단계, 수동 리깅 |
| 그림 보유자 | 직접 그렸거나 사용 권한이 있는 한 장의 그림을 보유 | 그림의 인상을 유지하며 움직이는 캐릭터 제작 | 부위 분리, 가려진 영역 보완, 움직임 설정 |
| 성장 사용자 | 기본 제작을 경험하고 더 정교한 결과를 원함 | 분리된 부위를 가져와 세밀한 표정과 움직임 구현 | 복잡한 역할 연결과 반복 설정 |
| 외부 도구 사용자 | 다른 아바타 실행 도구나 제작 흐름을 사용 | 제작 결과를 자신의 작업 환경에서 재사용 | 내보내기 호환성, 설정 손실, 문제 원인 확인 |

사용자의 그림 실력과 도구 숙련도는 별개로 본다. 그림을 잘 그려도 레이어 구조나 방송 연결을 모를 수 있다. 숙련도를 초기 선택 하나로 고정하지 않고 필요한 시점에 세부 기능을 열 수 있게 한다.

### 4.1 대표 사용자 스토리

- US-01: 도구를 모르는 사용자로서, 파츠를 고르고 색을 바꾸는 것만으로 내 캐릭터를 만들고 싶다.
- US-02: 그림 한 장을 가진 사용자로서, 눈과 입을 직접 분리하지 않고 먼저 움직이는 결과를 보고 싶다.
- US-03: 자동 인식이 틀렸을 때, 전문 용어 대신 “눈 위치를 맞춰 주세요”라는 안내로 수정하고 싶다.
- US-04: 분리된 그림을 가진 사용자로서, 각 부위의 역할을 쉽게 연결하고 기본 움직임을 자동 적용하고 싶다.
- US-05: 방송 사용자로서, 만든 캐릭터를 카메라와 마이크에 연결하고 방송 화면에서 바로 확인하고 싶다.
- US-06: 외부 도구 사용자로서, 사용할 프로그램에 맞는 형식으로 내보내고 주의점을 미리 알고 싶다.
- US-07: 반복 사용자로서, 지난 프로젝트를 열어 옷이나 표정을 바꾸고 기존 설정을 재사용하고 싶다.
- US-08: 장기적으로, 같은 캐릭터의 그림과 외형 정보를 바탕으로 3D 캐릭터를 만들고 싶다.
- US-09: 장기적으로, 원하는 외형을 글로 설명하고 자체 모델이 생성한 결과를 제작 과정에 이어서 쓰고 싶다.

## 5. 제품 경험 원칙

1. **빈 캔버스보다 시작 경로를 먼저 제공한다.** 첫 화면에서 파츠 조합과 그림 가져오기를 바로 선택한다.
2. **자동 결과를 먼저 보여준다.** 설정을 모두 끝낸 뒤에야 움직임을 확인하는 구조를 피한다.
3. **자동 처리와 직접 수정은 이어진다.** 자동 처리에 실패해도 처음부터 다시 시작하지 않는다.
4. **질문은 필요한 부분에 한정한다.** 인식이 확실한 부위는 자동 연결하고 불확실한 부분을 확인한다.
5. **기본 화면은 쉬운 행동으로 설명한다.** “변형 메시”보다 “고개를 돌렸을 때 모양 다듬기”를 먼저 보여준다.
6. **세부 편집으로 갈수록 제어 범위를 넓힌다.** 단순한 안내 화면과 세부 편집 화면이 같은 프로젝트를 사용한다.
7. **제작 결과를 잃지 않는다.** 자동 생성, 재분석, 보정 전에 복구 가능한 상태를 보존한다.
8. **실제 사용까지 안내한다.** 편집 완료 이후 방송 연결과 내보내기를 제품 밖의 문제로 남겨두지 않는다.
9. **자동화의 한계를 설명한다.** 지원하지 못하는 그림이나 움직임을 정상 처리한 것처럼 표시하지 않는다.
10. **같은 캐릭터의 정보를 이어 쓴다.** 입력 방식이 달라도 공통 프로젝트로 합류하고 향후 3D·생성 기능도 이를 활용한다.

## 6. 전체 범위와 단계별 경계

### 6.1 입력에서 실제 사용까지

```text
[파츠 조합] ─────────┐
[한 장의 그림] ───────┼→ [공통 캐릭터 프로젝트]
[분리된 부위의 그림] ─┘            │
                                 ↓
                     [외형 확인·수정 / 움직임 준비]
                                 ↓
                      [표정·입·고개 움직임 설정]
                                 ↓
                       [결과 확인·프로젝트 저장]
                                 ↓
              ┌──────────────────┼──────────────────┐
              ↓                  ↓                  ↓
       [장치 연결·실행·방송] [외부 호환 내보내기]   [이미지 저장]

장기 확장:
[자체 모델 글 기반 생성] → [검토·수정] → [공통 캐릭터 프로젝트]
[캐릭터 그림·외형 정보] → [3D 제작·보정] → [3D 실행·방송·내보내기]
```

프로젝트 저장은 위 흐름 전반에서 가능해야 한다. 외부 내보내기나 이미지 저장이 프로젝트 저장을 대신하지 않는다. 이미지 저장은 외형 제작 후 움직임 설정 없이도 가능해야 하며, 이미지 저장과 외부 내보내기에 카메라·마이크 연결을 필수로 요구하지 않는다. 외부 내보내기에는 대상 형식에 필요한 구조와 설정을 검사한다. 장기 확장의 세부 모델·파일 구조는 아직 확정하지 않는다.

### 6.2 범위 구분

| 기능 영역 | 초기 2D 출시 범위 | 장기 필수 범위 / 보충 설명 |
|---|---|---|
| 파츠 기반 제작 | 포함 | 라이브러리 확장과 조합 품질 개선 |
| 한 장 그림 기반 제작 | 포함 | 지원 가능한 그림·표현 범위 확대 |
| 분리된 그림 기반 제작 | 포함 | 복잡한 부위 구조와 세부 제어 확대 |
| 이미지 결과물 | 포함 | 사용 목적별 출력 옵션 확대 |
| 표정과 반응 | 포함 | 사용자 정의와 세밀한 움직임 확대 |
| 실시간 추적 | 포함 | 검증된 추적 범위부터 제공하고 범위를 확대 |
| 앱 내 아바타 실행 | 포함 | 장시간 실행 안정성 강화 |
| 방송 프로그램 연결 | 포함 | 검증된 연결 방식·대상부터 지원 |
| 외부 아바타용 내보내기 | 포함 | 최소 하나의 검증된 대상·형식 필요. 이후 확대 |
| 프로젝트 저장·재편집 | 포함 | 버전 호환 및 복구 강화 |
| 그림 기반 3D 제작 | 초기 출시 필수 완료 조건에서는 제외 | 전체 제품의 필수 확장. 별도 연구·제작 단계 필요 |
| 자체 모델 글 기반 생성 | 구체 설계와 구현을 후속 단계로 이관 | 전체 제품의 필수 확장. 자체 모델 제작·연결 방향 유지 |

초기 구현에서 모든 그림, 모든 방송 프로그램, 모든 외부 형식을 지원한다고 약속하지 않는다. 대신 공개한 지원 범위 안에서 제작부터 사용까지 완결되어야 한다. 지원 범위를 좁히는 결정은 검증 자료와 함께 기록한다.

### 6.3 현재 확정하지 않는 인접 기능

소셜 커뮤니티, 캐릭터 판매 장터, 공동 편집, 모바일 동시 지원, 전신 모션 캡처, 방송 송출·채팅 전체 관리 기능은 현재 필수 요구사항이 아니다. 필요성을 검토할 수 있으나 핵심 제작·사용 흐름보다 먼저 개발할 근거로 삼지 않는다.

## 7. 대표 사용 흐름

### 7.1 처음 사용하는 사람: 한 장의 그림에서 방송까지

1. 첫 화면에서 “내 그림으로 만들기”를 선택한다.
2. 그림 한 장을 가져온다. 프로그램은 읽을 수 있는지, 캐릭터를 식별할 수 있는지 검사한다.
3. 프로그램이 캐릭터 영역, 얼굴, 눈, 입 등 필요한 부위를 분석한다.
4. 준비된 영역부터 움직임 미리보기를 제공한다. 아직 추적 장치를 연결할 필요는 없다.
5. 불확실한 부분만 질문한다. 예: “왼쪽 눈 위치를 맞춰 주세요”, “입이 닫힌 위치를 확인해 주세요”.
6. 사용자는 기본 표정과 눈 깜빡임, 말할 때의 입 움직임, 고개 움직임을 확인하고 보정한다.
7. 카메라와 마이크를 선택하고 중립 자세를 맞춘다. 음성 반응과 카메라 추적의 입력 역할을 구분해 보여준다.
8. “방송에 사용하기”에서 출력 방식을 선택하고 대상 방송 프로그램의 연결 안내를 확인한다.
9. 실제 방송 프로그램의 미리보기에서 캐릭터, 투명 배경, 움직임을 확인한다.
10. 프로젝트를 저장하고 실행 화면으로 전환한다. 이후 다시 열어 같은 캐릭터를 실행할 수 있다.

완료 조건은 편집기의 애니메이션 재생이 아니라 **실제 방송 프로그램의 화면에서 캐릭터가 정상 작동하는 것**이다. 공개 방송 시작을 강제하지 않고 방송 프로그램의 미리보기로 연결을 검증할 수 있게 한다.

### 7.2 준비된 파츠로 제작

1. “파츠로 만들기”를 선택하고 기본 캐릭터 또는 몸체를 고른다.
2. 얼굴, 눈, 눈썹, 입, 머리카락, 의상, 장식 등을 고른다. 초기 제공 부위 목록은 별도 확정한다.
3. 파츠 교체와 색상·크기·위치 변경 결과를 즉시 확인한다.
4. 겹침이나 움직임 호환에 문제가 있으면 원인과 대체 선택을 보여준다.
5. 기본 움직임을 적용하고 사용자 취향에 맞게 표정과 반응을 조절한다.
6. 공통 추적·방송·내보내기 흐름으로 이동한다.

### 7.3 부위가 나뉜 그림으로 제작

1. 지원하는 레이어 파일 또는 분리 이미지 묶음을 가져온다. 실제 지원 형식은 검증 후 확정한다.
2. 부위 이름, 위치, 형태를 참고해 역할과 겹침 순서를 자동으로 제안한다.
3. 자동 인식 결과를 그림과 함께 보여주고 미확인 항목만 확인한다.
4. 눈, 입 등 필수 부위가 없으면 해당 움직임의 제한과 보완 방법을 안내한다.
5. 기본 움직임을 적용하고 같은 미리보기·보정 화면으로 이동한다.
6. 필요한 경우 세부 편집을 열어 부위 구조와 움직임을 조정한다.

### 7.4 기존 캐릭터를 수정한 뒤 다시 사용

1. 최근 프로젝트에서 캐릭터를 연다.
2. 저장된 상태로 바로 실행하거나 편집을 시작한다.
3. 외형 변경 시 기존 움직임에 영향을 주는 부위를 알려준다.
4. 수정 전 상태로 되돌리거나 변경본을 별도 버전으로 저장할 수 있다.
5. 움직임을 다시 확인하고 방송 출력 또는 내보내기를 갱신한다.

### 7.5 외부 프로그램에서 사용

1. 사용할 외부 프로그램 또는 지원 형식을 선택한다.
2. 프로그램이 현재 캐릭터의 호환성을 검사한다.
3. 지원되는 기능, 변환되는 기능, 손실되거나 사용할 수 없는 기능을 구분해 보여준다.
4. 필수 누락 항목을 수정하거나, 허용 가능한 제한을 확인하고 내보낸다.
5. 결과 파일과 필요한 동반 리소스를 저장하고 가져오기 방법을 안내한다.
6. 검증 대상 외부 프로그램에서 실제로 불러와 표시·움직임·표정이 작동하는지 확인한다.

### 7.6 01단계에서 고정한 시나리오

[기획 기준 3~4절](./planning/01-product-baseline.md)에 세 입력 경로의 진입, 프로젝트 저장·움직임·실행·실제 방송 확인·재개를 연결했다. 이미지 저장·프로젝트 저장·외부 아바타 내보내기의 목적·선행 조건·완료 차이도 구분했다. 각 경로의 제품 검증은 후속 구현에서 별도로 수행한다.

## 8. 화면 구성과 사용성 요구사항

### 8.1 주요 화면 제안

| 화면 | 목적 | 핵심 요소 |
|---|---|---|
| 시작 / 프로젝트 목록 | 제작 시작과 기존 캐릭터 재사용 | 제작 방식 선택, 최근 프로젝트, 바로 실행, 복구 알림 |
| 가져오기 / 분석 | 입력 검증과 자동 준비 | 파일 선택, 그림 미리보기, 분석 단계, 취소·재시도 |
| 캐릭터 편집 | 외형과 움직임 완성 | 중앙 미리보기, 현재 단계 안내, 관련 설정, 되돌리기 |
| 간단 보정 | 자동 인식 오류 수정 | 위치 표시, 쉬운 질문, 수정 전후 비교, 건너뛰기 시 영향 |
| 세부 편집 | 숙련 사용자의 제어 | 부위 목록, 겹침 순서, 연결, 변형과 움직임 범위 |
| 장치 연결 / 보정 | 입력과 캐릭터 움직임 연결 | 장치 선택, 입력 상태, 중립 보정, 반응 미리보기 |
| 실행 / 방송 | 안정적인 실제 사용 | 큰 캐릭터 미리보기, 출력 상태, 표정 단축키, 추적 복구 |
| 내보내기 | 외부 활용 | 대상 선택, 호환성 검사, 제한 안내, 저장 위치, 사용 안내 |
| 설정 | 환경 조절 | 장치, 저장, 성능, 개인정보, 입력 키 설정 |

### 8.2 공통 UX 요구사항

- 현재 단계, 완료된 단계, 다음 행동을 표시한다. 이전 단계로 돌아가도 결과를 보존한다.
- 전문 용어는 도움말과 세부 편집에서 설명하고, 기본 조작은 사용자가 원하는 결과 중심으로 표현한다.
- 파일 끌어놓기와 선택 버튼 등 입력 방법을 제공하되 실제 지원 방식은 플랫폼 설계에서 확정한다.
- 오류는 원인, 영향을 받는 기능, 다음 행동을 포함한다. 오류 코드만 표시하지 않는다.
- 오래 걸리는 작업은 진행 단계와 취소 가능 여부를 표시한다. 처리 시간 추정이 불확실하면 임의의 시간을 약속하지 않는다.
- 색만으로 상태를 구분하지 않는다. 텍스트·아이콘을 함께 제공한다.
- 자동 처리 결과와 사용자가 직접 수정한 부분을 구분한다. 재분석 시 사용자 수정을 보호한다.
- 방송 출력에는 편집용 선택선, 보정점, 도움말, 오류창이 포함되지 않게 한다.

## 9. 기능 요구사항: 프로젝트와 입력

### FR-PROJ-01. 공통 프로젝트 생성·저장·재개

- 모든 초기 제작 방식은 같은 프로젝트 체계로 합류해야 한다.
- 원본 입력, 편집 결과, 부위 구조, 움직임, 표정, 실행 설정, 내보내기 설정을 저장한다.
- 프로젝트에는 고유 ID와 파일 구조 버전을 포함한다.
- 프로젝트 다시 열기, 다른 이름으로 저장, 복제 기능을 제공한다.
- 프로젝트를 옮겨도 필요한 리소스가 누락되지 않도록 상대 경로나 묶음 저장 등 재현 가능한 방식을 설계한다.
- 장치별 설정은 사용자 환경 설정과 분리한다. 다른 기기에서 열었을 때 기존 장치가 없으면 재선택을 안내한다.

### FR-PROJ-02. 자동 저장과 복구

- 자동 저장과 명시적 저장을 구분하고 마지막 저장 상태를 보여준다.
- 자동 분석·분리·재생성 등 큰 변경 전 복구 지점을 만든다.
- 비정상 종료 후 복구 가능한 상태를 탐지하고 복원 여부를 선택하게 한다.
- 저장 중 오류가 발생해도 기존 정상 저장본을 훼손하지 않도록 설계한다.
- 되돌리기와 다시 실행을 제공한다. 되돌릴 수 없는 작업은 실행 전에 결과와 영향을 알린다.

### FR-INPUT-01. 입력 파일 검사

- 파일의 읽기 가능 여부, 지원 형식, 크기·해상도 제한, 투명도, 리소스 누락을 확인한다.
- 초기 한 장 그림 경로는 최소 하나 이상의 일반적인 래스터 이미지 형식을 지원해야 한다. 구체 목록과 상한은 검증 후 확정한다.
- 분리 그림 경로는 레이어를 보존하는 파일 또는 개별 부위 이미지 묶음을 지원해야 한다. 05에서 투명 PNG 폴더/`.2dparts`를 최초 형식으로 채택했으며 PSD 직접 입력은 후속 검증으로 남긴다.
- 여러 캐릭터가 있는 그림은 사용할 캐릭터를 선택하게 하거나 지원 제한을 설명한다.
- 캐릭터 일부가 잘렸거나 배경과 섞여 있으면 예상 영향을 설명하고 자르기·영역 선택 등 보완 경로를 제공한다.
- 원본을 보존하고 내부 편집용 리소스를 별도로 관리한다.

### FR-INPUT-02. 분석 상태와 재시도

- 읽기 → 영역 확인 → 부위 분석 → 움직임 준비 등 실제 처리 단계에 맞는 상태를 제공한다.
- 취소해도 이미 저장된 프로젝트와 원본은 유지한다.
- 실패한 단계부터 재시도할 수 있도록 설계한다. 재시도로 보정값을 덮어쓸 경우 먼저 선택하게 한다.
- 실패한 입력에 대해 지원하지 않는 이유와 가능한 대체 제작 경로를 제시한다.

## 10. 기능 요구사항: 캐릭터 외형 제작

### 10.0 이미지 품질 기준 — 사용자 추가 요구

**NFR-ART-01:** 이미지 결과와 제공 아트는 사용자가 요청한 “고급스럽고 GPT Image 2.0 느낌의 완성도”를 지향한다. 이를 섬세한 선화, 얼굴·눈동자 인상, 머리카락 가닥과 명암, 의상 재질·장식의 정교함 및 처리 후 원화 보존으로 평가한다. 해상도 수치만으로 통과시키거나 원화를 단순한 도형·색면으로 바꾸어 품질 문제를 숨기지 않는다.

02에서 [고품질 원화 입력](./planning/02-readiness.md)과 [원본 크기·실제 출력 크기의 비교 평가](./planning/02-evaluation.md)를 준비했다. 단순 절차 fixtures는 구조·오류 검사에 사용한다. 고품질 입력이 확보되었다는 사실은 자동 분리·리깅·출력 품질 통과를 뜻하지 않는다. `GPT Image 2.0`은 사용자의 시각적 품질 참조이며 특정 외부 생성 API를 제품 필수 의존성으로 정하거나 자체 모델 생성의 완료를 대체하는 요구가 아니다.

### FR-PART-01. 파츠 라이브러리와 조합

- 부위별 파츠 목록과 적용 미리보기를 제공한다.
- 조합 가능한 기본 몸체·파츠 간 관계를 정의하고 호환되지 않는 조합을 판별한다.
- 눈, 입 등 움직이는 파츠는 기본 움직임 정보와 함께 제공한다.
- 파츠 교체 후에도 유지할 수 있는 색상·표정·추적 설정은 보존한다.
- 사용자에게 선택지를 제공할 만큼 초기 파츠 구성이 필요하다. 수량은 아트 제작 계획에서 결정한다.
- 제공 파츠의 제작자, 출처, 사용 범위 등 필요한 메타데이터를 관리한다.

### FR-PART-02. 외형 조절

- 파츠 색상, 허용 범위 내 크기·위치·회전을 조절한다.
- 좌우 연동과 개별 조절을 필요한 부위에 제공한다.
- 조절 범위는 움직임 중 심한 찢어짐이나 겹침 오류를 줄이도록 파츠별로 정의한다.
- 기본값 복원, 변경 전후 비교, 조합 저장을 지원한다.

### FR-IMG-01. 한 장 그림의 자동 구조화

- 캐릭터 영역과 움직임에 필요한 부위를 최대한 자동으로 찾는다.
- 초기 핵심 대상은 얼굴, 눈, 눈썹, 입, 머리와 기본 몸통의 관계다. 실제 자동 분리 가능 범위는 기술 검증으로 확정한다.
- 움직임에 필요한 분리·변형 구조와 기본 반응을 생성한다. 사용자에게 메시 작성이나 직접 리깅을 필수로 요구하지 않는다.
- 원화의 색, 선, 인상을 가능한 한 유지한다. 보완된 영역과 원본 영역을 확인할 수 있게 한다.
- 부위 인식의 불확실성을 내부적으로 관리하고 사용자 확인이 필요한 항목을 추린다.
- 자동 분리 결과를 수정할 수 있어야 하며, 원본을 덮어쓰지 않는다.

### FR-IMG-02. 가려진 영역과 움직임 한계 처리

- 한 장의 그림에서 보이지 않는 입 안, 눈 뒤, 머리카락 뒤 등은 원래 모습을 알 수 없다는 제약을 반영한다.
- 보완이 필요한 경우 프로그램의 추정 결과를 보여주고 사용자가 수정·선택할 수 있게 한다.
- 초기 보완 방식은 미정이다. 자체 모델 글 기반 생성 기능의 선행 완성을 요구하지 않는 대체 방식도 검토한다.
- 보완 품질이 부족하면 움직임 범위를 제한하거나 지원 가능한 표현으로 안내한다.
- 완전한 측면·후면이나 큰 고개 회전이 자동 복원된다고 약속하지 않는다.
- 처리 실패를 숨기기 위해 원화와 크게 다른 외형으로 바꾸지 않는다. 변경이 필요하면 사용자가 확인한다.

### FR-IMG-03. 쉬운 보정

- 눈·입 등 위치 확인, 부위 영역 수정, 앞뒤 순서 변경을 그림 위에서 수행한다.
- “입 위치 맞추기”, “머리카락 뒤쪽 확인하기”처럼 구체적인 행동을 안내한다.
- 수정한 부분의 움직임을 즉시 또는 짧은 재처리 후 확인할 수 있게 한다.
- 보정을 건너뛰면 어떤 표현이 제한되는지 설명한다.
- 자동 결과로 돌아가기와 보정 전 상태 복원을 제공한다.

### FR-LAYER-01. 분리된 그림 가져오기와 역할 연결

- 원본 부위 이름, 순서, 투명도, 위치 관계를 지원 범위 안에서 보존한다.
- 이름만 믿고 연결하지 않고 위치·형태 등 가능한 정보를 함께 활용한다.
- 왼쪽·오른쪽 기준을 명확하게 표시한다. 예: 캐릭터 기준과 화면 기준의 혼동 방지.
- 역할이 같은 복수 부위, 역할 미지정 부위, 빈 부위, 필수 부위 누락을 구분한다.
- 자동 제안을 적용하기 전 또는 미리보기 중 수정할 수 있게 한다.
- 구조가 준비된 그림에는 기본 연결과 움직임을 적용하고 이후 편집 흐름에 합류시킨다.

### FR-EDIT-01. 세부 편집

- 부위 이름·역할·겹침 순서·연결 관계를 수정한다.
- 움직임의 기준점, 영향 범위, 변형 정도를 확인하고 조절할 수 있게 한다.
- 간단 편집에서 만든 결과를 세부 편집으로 옮길 때 새 프로젝트를 강제하지 않는다.
- 세부 편집 후에도 실행·방송·내보내기 가능 상태를 검사할 수 있어야 한다.
- 세부 구조 변경으로 자동 설정이 무효화되면 영향을 받는 항목만 재설정하게 한다.

## 11. 기능 요구사항: 표정과 움직임

### FR-MOTION-01. 기본 움직임과 미리보기

- 눈 깜빡임, 눈의 열림 정도, 입의 열림 정도, 제한된 고개 움직임을 초기 핵심 대상으로 한다.
- 실제 제공 범위와 정밀도는 지원 그림 조건 및 추적 방식과 함께 확정한다.
- 카메라 없이도 예제 동작이나 조절 막대로 각 움직임을 확인할 수 있어야 한다.
- 기본 자세, 최소·최대 범위, 움직임 세기와 부드러움을 설정한다.
- 극단적인 입력에서도 심한 변형이 발생하지 않도록 허용 범위를 정의한다.
- 머리카락·장식의 보조 흔들림은 우선 검토 대상이다. 초기 필수 여부는 핵심 얼굴 움직임 검증 후 결정한다.

### FR-MOTION-02. 표정과 상태

- 기본 표정으로 돌아오기와 사용자 정의 표정 저장을 지원한다.
- 표정에는 눈·눈썹·입 등 여러 부위의 설정을 함께 저장할 수 있다.
- 표정 전환에 단축키 또는 화면 버튼을 연결한다.
- 수동 표정, 자동 깜빡임, 카메라 입력, 마이크 입력이 같은 부위를 제어할 때의 우선순위를 명시한다.
- 예: 특정 표정에서 눈을 고정할 경우 추적 입력을 해당 부위에만 제한한다. 구체 정책은 편집 화면에서 확인 가능해야 한다.
- 표정 전환 중에도 불필요한 순간 이동이나 출력 끊김을 줄인다.

### FR-MOTION-03. 음성 반응

- 마이크 입력의 유무와 크기에 따라 말하는 반응을 만들 수 있어야 한다.
- 입력 장치, 감도, 조용할 때의 기준, 입 움직임 세기를 조절한다.
- 주변 소음으로 입이 계속 움직이지 않도록 조절 및 미리보기 경로를 제공한다.
- 카메라의 입 추적과 마이크 반응 중 사용할 방식을 고르거나 결합 정책을 명시한다.
- 음소별 정밀 입 모양이나 음성 인식은 초기 필수로 확정하지 않는다.
- 마이크 분석이 방송용 음성 녹음·송출과 같은 기능이라고 오해하지 않도록 설명한다.

## 12. 기능 요구사항: 추적과 앱 내 실행

### FR-TRACK-01. 카메라 연결과 보정

- 사용 가능한 카메라를 나열하고 선택한 입력과 인식 상태를 보여준다.
- 중립 자세를 기준으로 얼굴 위치와 움직임 범위를 보정할 수 있어야 한다.
- 입력 움직임과 캐릭터 반응 사이의 방향·강도·부드러움을 조절한다.
- 카메라 권한 거부, 장치 없음, 다른 프로그램의 장치 점유, 얼굴 미검출을 구분한다.
- 여러 얼굴이 잡힐 때의 처리 정책을 명시하고 대상이 임의로 바뀌지 않도록 한다.
- 보정 과정은 전문 장비나 신체 수치 입력을 기본 조건으로 요구하지 않는다.

### FR-TRACK-02. 입력 누락과 복구

- 얼굴이 잠깐 사라지거나 입력이 끊기면 정해진 대체 동작으로 전환한다.
- 대체 동작은 마지막 자세 유지, 기본 자세 복귀, 자동 깜빡임 등에서 검증 후 선택한다.
- 비정상적으로 큰 입력이나 떨림을 완화하고 캐릭터 변형 범위를 제한한다.
- “추적 다시 맞추기”와 장치 재연결을 실행 화면에서 빠르게 수행한다.
- 추적 실패를 방송 화면의 오류창으로 노출하지 않는다. 사용자용 제어 화면에서 상태를 알린다.

### FR-RUN-01. 독립된 실행 경험

- 저장된 캐릭터를 열어 편집 과정을 반복하지 않고 실행할 수 있어야 한다.
- 실행 화면에서는 캐릭터 상태, 장치, 출력, 표정 전환, 복구 동작에 집중한다.
- 편집 화면과 실행 화면은 역할을 구분하되 같은 프로젝트를 사용한다.
- 편집 결과를 실행 중에 반영하는 범위와 다시 시작해야 하는 변경을 구분한다.
- 실행 중 프로젝트 전환 시 저장되지 않은 변경과 출력 영향을 안내한다.
- 실행을 중지해도 프로젝트 데이터가 사라지지 않는다.

## 13. 기능 요구사항: 방송 연결

### FR-BROAD-01. 방송용 출력

- 캐릭터를 실제 방송 프로그램에서 영상 소스로 사용할 수 있어야 한다.
- 투명 배경을 지원하는 출력 경로를 초기 필수 목표로 두고, 검증한 연결 방식에 맞게 제공한다.
- 캐릭터 크기, 화면 내 위치, 자르기 범위, 출력 해상도·프레임 설정을 지원 범위 안에서 조절한다.
- 편집 UI, 파일 경로, 카메라 원본, 마이크 상태창 등은 캐릭터 출력에 섞이지 않아야 한다.
- 외부 출력과 사용자용 미리보기의 역할을 구분한다.
- 05에서 OBS 33.0.1 Browser Source의 로컬 투명 출력과 앱/OBS 공유 WebGL2 렌더러를 최초 방식으로 채택했다. 새 GPU 경로의 실제 성능·알파·재연결은 M0 재검증 대상이다. 창 캡처·가상 장치·Spout/NDI는 최초 보증에서 제외한다.

### FR-BROAD-02. 연결 안내와 검증

- 초기 지원 방송 프로그램과 버전, 운영체제, 연결 방식을 명시한다.
- 초보자가 소스를 추가하고 캐릭터를 배치하는 과정을 순서대로 안내한다.
- “우리 앱에서 출력 준비 완료”와 “대상 프로그램에서 수신 확인 완료”를 구분한다.
- 외부 프로그램의 상태를 자동 확인할 수 없으면 사용자 확인 절차를 제공하고 자동 검증한 것처럼 표시하지 않는다.
- 배경이 불투명함, 소스가 보이지 않음, 캐릭터가 잘림, 움직임이 멈춤 등에 대한 진단 항목을 제공한다.
- 방송 플랫폼 계정 연결이나 스트리밍 서버 송출은 현재 제품의 필수 범위가 아니다.

### FR-BROAD-03. 방송 중 조작과 안정성

- 표정 전환, 기본 자세 복귀, 추적 재보정, 캐릭터 출력 숨김을 빠르게 수행할 수 있게 한다.
- 단축키 충돌과 사용 가능 범위를 알려준다. 다른 앱이 선택되어 있을 때 작동해야 하는 키는 별도 검증한다.
- 카메라·마이크 재연결이나 설정 변경이 캐릭터 출력에 미치는 영향을 예측 가능하게 한다.
- 처리 부하가 높으면 해상도·효과 등 품질 조절로 대응할 수 있게 한다.
- 자동 품질 조절을 제공한다면 현재 적용 상태를 표시하고 사용자가 제어할 수 있게 한다.

## 14. 기능 요구사항: 결과물과 내보내기

### FR-EXPORT-01. 캐릭터 이미지 저장

- 현재 외형과 선택한 표정을 이미지로 저장할 수 있어야 한다.
- 투명 배경과 배경 포함 출력을 지원 범위에 맞게 제공한다.
- 출력 크기와 캐릭터 배치를 미리 확인한다.
- 이미지 저장은 움직이는 캐릭터용 내보내기와 별도 메뉴·설명으로 구분한다.

### FR-EXPORT-02. 외부 아바타용 내보내기

- 외부 프로그램에서 사용 가능한 움직이는 캐릭터 결과물을 내보내야 한다.
- 초기 출시에는 최소 하나의 외부 대상·형식을 선정해 실제 구동을 검증한다.
- 단순 이미지 저장, 자체 프로젝트 저장, 동영상 저장만으로 이 요구사항을 충족했다고 판단하지 않는다.
- 대상 형식에서 표현 가능한 외형·부위·움직임·표정·기본값을 변환한다.
- 필요한 텍스처, 설정, 관련 파일을 누락 없이 묶거나 지정된 구조로 저장한다.
- 내보낸 결과와 원본 프로젝트의 연결 정보를 남겨 같은 대상에 다시 내보내기 쉽게 한다.
- 특정 상용 도구의 네이티브 형식 지원, 공식 연동, 모든 효과의 보존은 별도 검증 없이 약속하지 않는다.

### FR-EXPORT-03. 호환성 사전 검사

- 대상별 필수 항목, 지원되지 않는 움직임, 텍스처 제한, 이름 규칙 등 확인 가능한 조건을 검사한다.
- 결과를 `통과`, `경고`, `차단`으로 구분한다.
- 경고는 손실과 대체 결과를 설명하고, 차단은 수정 경로를 제공한다.
- 대상이 지원하지 않는 핵심 기능을 조용히 제거하지 않는다.
- 실제 수신 프로그램에서 열기 전에는 “파일 생성 완료”와 “외부 구동 확인”을 구분한다.
- 내보내기 실패 시 불완전한 결과가 정상 완료 파일로 남지 않도록 설계한다.

### 14.1 지원 대상·형식 결정표

05단계에서 다음 최초 범위를 구현 목표로 채택했다. 현재 전체 호환 보증 목록은 아니며, 출시 지원표에는 실제 통과한 OS·입력·대상/버전만 올린다. 한 장/분리/파츠 세 경로와 앱 내 실행·외부 내보내기는 모두 필수로 유지한다.

| 용도 | 최초 결정 | 통과 기준 |
|---|---|---|
| 한 장 그림 입력 | PNG RGB/RGBA 8bit·JPEG RGB, 256~4096px/한 변·16MP 이하, 정면/작은 기울기의 1캐릭터 우선. 상세 DEC-02 | 정상 디코드/원본 보존과 조건별 자동 준비·보정 확인. 03 실측 한도보다 큰 4096px는 추가 검증 필요 |
| 분리 그림 입력 | 투명 PNG 폴더·`.2dparts` ZIP, 공통 캔버스 또는 명시 원점, 최대 64부위·normal 합성. PSD 직접 입력은 최초 제외 | 순서·좌표·역할·그룹 opacity 재현, 쉬운 안내, 잘못된 경로/묶음 차단 |
| 프로젝트 저장 | `.2dsketch` v1 ZIP, 원본/파생·manifest SHA-256·상태/망/표정/출처. 정상본 5·복구본 5 정책 | 이동/정상본 보호·취소/실패·해시/버전·복구를 실제 제품에서 확인 |
| 이미지 출력 | PNG RGBA 8bit/sRGB, 지정 크기와 투명 배경 | 실제 출력 크기의 원화 인상·알파/색 보존 확인 |
| 방송 출력 | Windows 11 x64, OBS Studio 33.0.1 Browser Source, 로컬 공유 WebGL2, 1080p/30FPS 목표 | 새 GPU 경로의 실제 투명도·성능·재연결 검증. 기존 PNG 전달 성공은 새 엔진 합격을 대신하지 않음 |
| 2D 아바타 내보내기 | INP, Inochi Session v0.8.7 / SDK v0.8.6, 기본 제어/표정·텍스처 내장 | 앱/서버 종료 뒤 실제 로드·사용과 내부/외부 표현·손실 검사. 핵심 기능 조용한 손실 금지 |
| 3D 아바타 내보내기 | 후속 3D 대상·형식, 리그·표정 규칙 | 3D 단계에서 별도 정의 및 검증 |

외부 형식 선정 시 기술적 구현 가능성, 사양 접근성, 배포·사용 조건, 사용자 수요, 표현 손실을 함께 검토한다. 대상 선정은 초기 기술 검증 단계에서 진행한다. 초기 내보내기를 후속 단계로 무기한 미루지 않는다.

## 15. 필수 장기 확장: 그림 기반 3D 캐릭터

### 15.1 목적과 경계

그림과 기존 캐릭터의 외형 정보를 활용해 입체적인 3D 캐릭터를 만들고, 수정·실행·방송·내보내기로 이어지게 한다. 초기 2D 결과물을 단순 변환하면 동일한 품질의 3D가 자동 완성된다고 전제하지 않는다.

2D에서 표현하는 고개 움직임이나 평면 변형을 완전한 3D 제작 완료로 간주하지 않는다. 3D 확장은 입체 형상, 재질·텍스처, 움직임 구조와 표정을 갖는 캐릭터를 대상으로 한다.

### 15.2 장기 요구사항

- FR-3D-01: 한 장 또는 복수의 참고 그림과 기존 외형 정보를 입력으로 활용한다. 실제 지원 입력 조건은 연구 단계에서 확정한다.
- FR-3D-02: 보이지 않는 옆면·뒷면과 깊이 구조에 대한 추정 결과를 보여주고 수정할 수 있게 한다.
- FR-3D-03: 원화와의 유사성, 정면 인상, 옆면과 뒷면, 표정 변형을 각각 확인한다.
- FR-3D-04: 초보자가 전문 모델링 도구를 배우지 않고 주요 형태와 색상을 조절할 수 있는 경로를 제공한다.
- FR-3D-05: 방송용 움직임 추적과 표정 연결을 지원하고 3D 출력도 방송 프로그램에서 검증한다.
- FR-3D-06: 외부 3D 아바타용 내보내기 대상을 별도로 정하고 호환성을 검사한다.
- FR-3D-07: 원본 2D 프로젝트를 보존하고 3D 파생 결과를 구분해 저장한다.
- FR-3D-08: 자동 제작에 실패한 부분을 알려주고 보정 또는 지원 제한을 제시한다.

### 15.3 선행 검증 과제

- 입력 그림의 구도·화풍에 따른 복원 가능 범위와 품질 편차.
- 원화의 인상을 유지하면서 가려진 형태를 제안하는 방법.
- 입체 형상과 움직임 구조를 초보자가 수정하는 경험.
- 제작 시간, 필요한 장비, 실행 성능, 저장 용량.
- 학습 모델을 활용한다면 데이터와 모델의 사용·배포 조건.

3D 제공 시점은 확정하지 않는다. 독립적인 기술 검증과 수용 기준을 거쳐 단계적으로 제공한다.

## 16. 필수 장기 확장: 자체 모델 글 기반 생성

### 16.1 확정 방향

사용자가 외형을 글로 설명하면 **자체 모델을 제작하고 연결해** 캐릭터 생성 결과를 제공한다. 외부 생성 API를 호출하는 기능을 이 요구사항의 최종 구현으로 대체하지 않는다. 외부 API 의존을 전제로 한 기획을 기본안으로 두지 않는다.

이번 초기 기획에서는 모델 구조, 학습 방식, 데이터 규모, 학습·추론 인프라, 일정의 구체 설계를 보류한다. 자체 모델을 처음부터 학습할지, 활용 가능한 기반 모델을 바탕으로 개발할지 등 “자체 제작”의 기술적 범위는 별도 결정이 필요하다. 어느 방향이든 단순 외부 API 연결로 축소하지 않는다는 제품 방향은 유지한다.

### 16.2 장기 요구사항

- FR-GEN-01: 사용자가 자연어로 외형을 설명하고 생성 결과를 검토할 수 있어야 한다.
- FR-GEN-02: 생성 결과를 선택·수정한 뒤 공통 캐릭터 제작 흐름으로 이어갈 수 있어야 한다.
- FR-GEN-03: 정적인 생성 이미지와 움직임에 바로 사용할 수 있는 구조화된 결과를 구분한다. 이미지 생성만으로 자동 리깅까지 완료했다고 표시하지 않는다.
- FR-GEN-04: 원래 입력한 설명, 사용 모델 버전, 선택 결과와 수정 이력을 프로젝트에서 필요한 범위로 관리한다.
- FR-GEN-05: 생성 결과가 파츠·레이어·움직임과 연결되는 방식은 별도 설계한다.
- FR-GEN-06: 제작자의 원본 그림이나 캐릭터를 학습에 활용하는 정책은 명확한 동의와 권한을 바탕으로 별도 정의한다.
- FR-GEN-07: 처리 실패, 긴 대기, 취소와 재시도 상황을 고려한다.
- FR-GEN-08: 로컬 추론과 자체 운영 서버 추론 중 제공 방식을 검토하고 필요한 장비·네트워크·비용을 설명한다.

### 16.3 착수 전에 결정할 사항

| 영역 | 결정할 내용 |
|---|---|
| 모델 목표 | 이미지 생성 우선인지, 움직임 제작에 적합한 구조화 결과까지 목표로 하는지 |
| 자체 개발 범위 | 기반 모델 활용 범위, 직접 학습·개선할 부분, 산출물 관리와 소유 범위 |
| 데이터 | 확보 방식, 사용 권한, 품질 기준, 편향·중복 관리, 삭제·추적 정책 |
| 학습 환경 | 장비, 예산, 학습 주기, 재현성, 평가 방식 |
| 추론 환경 | 로컬 / 자체 서버, 응답 시간, 운영 비용, 오프라인 지원 여부 |
| 품질 | 설명 반영, 외형 일관성, 보정 가능성, 움직임 제작 적합성 |
| 제품 연결 | 기존 그림 가져오기·파츠 편집·3D 제작과의 연결 방식 |

자체 모델 생성의 선행 완성을 초기 파츠·그림 기반 2D 제작의 출시 조건으로 두지 않는다. 이미지 분석과 자동 움직임 준비에 어떤 기술을 사용할지는 이 생성 기능과 구분해 검토한다.

## 17. 프로젝트 데이터와 상태 관리

### 17.1 공통 데이터 구성 제안

| 데이터 | 주요 내용 | 관리 원칙 |
|---|---|---|
| 프로젝트 | ID, 이름, 버전, 생성·수정 시점, 입력 경로 유형 | 재개와 호환성 판단의 기준 |
| 원본 리소스 | 가져온 그림, 분리 부위, 사용한 기본 파츠 | 원본 보존, 출처·참조 관계 관리 |
| 캐릭터 구조 | 부위 ID, 역할, 좌표, 앞뒤 순서, 연결 관계 | 표시 이름 변경으로 참조가 끊기지 않게 관리 |
| 편집 리소스 | 분리 영역, 보완 그림, 텍스처, 변형 데이터 | 원본과 분리, 재생성·수정 이력 추적 |
| 움직임 | 매개변수, 범위, 부위 연결, 보간·흔들림 설정 | 입력 장치와 분리된 캐릭터 제어 규칙 |
| 표정 | 이름, 부위별 값, 전환 방식, 우선순위 | 추적 및 수동 입력 충돌 처리 |
| 추적 매핑 | 카메라·마이크 입력과 캐릭터 매개변수 연결 | 장치가 바뀌어도 캐릭터 구조 유지 |
| 실행 설정 | 기본 자세, 단축키, 품질, 출력 설정 | 기기별 설정과 프로젝트 설정 구분 |
| 내보내기 | 대상 프로필, 변환 결과, 경고, 사용한 버전 | 재내보내기와 문제 재현에 활용 |
| 장기 확장 정보 | 3D 파생 관계, 생성 설명·모델 버전 | 기존 2D 프로젝트를 훼손하지 않고 확장 |

### 17.2 상태 흐름

기본 작업 상태는 `입력 준비 → 분석 중 → 보정 필요 / 편집 가능 → 움직임 확인 → 실행 준비`로 정의한다. 실행 준비 이후 방송 출력과 내보내기는 각각의 검증 상태를 별도로 가진다.

- 분석 완료가 곧 방송 준비 완료를 의미하지 않는다.
- 방송 연결 실패가 곧 편집 데이터의 오류를 의미하지 않는다.
- 앱 내 실행 가능과 특정 외부 형식으로 내보내기 가능은 별도 판정한다.
- 상태를 되돌리거나 재분석해도 마지막 정상 프로젝트와 사용자의 보정 내용을 복구할 수 있어야 한다.
- 미리보기, 저장, 분석, 내보내기 작업의 충돌을 방지하고 처리 중 가능한 행동을 명확하게 한다.

### 17.3 기술 구조의 설계 원칙

입력 처리, 자동 분석, 캐릭터 편집, 움직임 평가, 실시간 실행, 방송 출력, 외부 변환을 책임별로 구분하는 구조를 제안한다. 내부 캐릭터 구조를 특정 외부 형식 하나에 종속시키지 않되, 외부 변환에 필요한 정보를 잃지 않게 설계한다.

초기에는 작은 규모로 구현할 수 있다. 모듈 구분이 별도 서비스 운영이나 복잡한 인프라를 반드시 뜻하지는 않는다. 05에서 **Electron/TypeScript·React UI + 앱/OBS 공유 WebGL2 렌더러 + 별도 Python 분석/추적 worker + INP adapter**를 채택했다. 로컬 2D 처리·Windows 11 x64 포터블 EXE/ZIP을 기본으로 하고, 제품 새 엔진의 실행/포장 검증은 M0-R01/R05에 남긴다. [스택·버전·조건·대안](./planning/05-stack.md)을 따른다.

저장은 원본/불변 리비전 스냅샷·동일 볼륨 임시 작성/검사·검증된 백업·원자 교체로 설계한다. 자동 복구는 유휴 15초 또는 최대 60초 간격, 지원 밖 버전은 안전한 읽기/차단 정책을 따른다. 분석·저장·내보내기는 project/revision/job/취소 세대로 격리하며 실행은 완성 스냅샷을 프레임 경계에서 교체한다. 전역 단축키는 기본 해제·선택 등록·충돌 안내·버튼 대체다. [DEC-08~12](./planning/05-decisions.md)의 정책 모델 31개 통과를 제품 통합 완료로 세지 않는다.

## 18. 비기능 요구사항

### 18.1 사용성

- NFR-UX-01: 처음 사용하는 사람이 레이어·리깅·메시 등의 개념을 몰라도 기본 흐름을 완료할 수 있어야 한다.
- NFR-UX-02: 자동 처리 실패 후 사용자가 다음 행동을 이해할 수 있어야 한다.
- NFR-UX-03: 주요 작업은 변경 전 상태로 되돌리거나 복구할 수 있어야 한다.
- NFR-UX-04: 주요 화면에서 키보드 이동, 명확한 초점 표시, 읽을 수 있는 글자·대비를 고려한다.
- NFR-UX-05: 지원하지 않는 기능과 아직 준비 중인 기능을 현재 사용 가능한 기능처럼 표시하지 않는다.

### 18.2 성능과 실행 품질

### 18.3 데이터 안정성과 호환성

- NFR-DATA-01: 저장 실패나 비정상 종료가 기존 정상 프로젝트를 훼손하지 않도록 한다.
- NFR-DATA-02: 프로젝트 파일 구조의 버전을 기록하고 지원하지 않는 버전은 명확하게 안내한다.
- NFR-DATA-03: 누락된 파일과 외부 경로 문제를 탐지하고 재연결할 수 있게 한다.
- NFR-DATA-04: 원본, 자동 생성 결과, 사용자 보정 결과의 관계를 추적한다.
- NFR-COMPAT-01: 지원 운영체제·방송 프로그램·외부 형식은 버전과 검증 범위를 공개한다.
- NFR-COMPAT-02: 의존 도구나 형식 변경 후 회귀 검증을 수행한다.

### 18.4 개인정보와 자산 처리

- 카메라·마이크 접근 전에 용도와 사용 상태를 설명한다.
- 원본 카메라 영상과 음성을 기본적으로 녹화·저장하지 않는 방향을 제안한다. 필요한 기능이 생기면 별도 동의와 정책을 설계한다.
- 로컬 처리를 우선 검토하되 확정된 구현 방식으로 간주하지 않는다. 서버 전송이 필요한 기능은 전송 대상, 목적, 보관·삭제 방식을 먼저 보여준다.
- 진단 로그에 원본 그림, 카메라 프레임, 음성, 개인 파일 경로가 불필요하게 포함되지 않도록 한다.
- 사용자 그림과 캐릭터를 학습에 자동 편입하지 않는다. 자체 모델 학습 활용은 별도 동의와 권한 정책을 정의한다.
- 제공 파츠, 분석·추적 구성요소, 내보내기 형식, 모델·데이터의 사용 및 배포 조건을 확인한다.
- 사용자에게 입력 자산의 권한 확인을 안내하되, 프로그램이 모든 권리 관계를 자동 보증하는 것으로 표시하지 않는다.

복구 과정에서 사용자의 원본이나 마지막 정상 상태를 자동으로 덮어쓰지 않는다. 복구 불가능한 경우에도 내보낼 수 있는 데이터와 실패 원인을 최대한 제공한다.

### 20.2 테스트 입력과 품질 평가

검증 자료는 다음 차이를 포함하도록 구성한다. 모두를 초기 지원한다고 선언하는 것은 아니며, 지원 경계와 실패 설명을 확인하기 위한 자료다.

- 파츠 조합: 기본 조합, 좌우 조절, 큰 장식, 머리·의상 겹침, 파츠 교체 후 설정 유지.
- 한 장 그림: 투명/불투명 배경, 정면/기울어진 얼굴, 눈·입 가림, 다양한 선과 채색, 잘린 몸체, 복수 캐릭터.
- 분리 그림: 알아보기 쉬운 이름/불명확한 이름, 누락 부위, 좌우 혼동, 여러 장식, 다른 크기의 이미지.
- 움직임: 정면 중립, 눈 감기, 말하기, 제한 끝의 고개 방향, 빠른 움직임, 표정과 추적 충돌.
- 환경: 권한 거부, 장치 변경, 낮은 조명, 소음, 높은 부하, 창 전환, 저장 공간 부족, 비정상 종료.
- 외부 사용: 지원 버전별 방송 연결, 투명도, 크기·잘림, 내보내기 후 텍스처·표정·움직임 재현.

품질은 원화 인상 유지, 경계·겹침 오류, 눈·입의 자연스러움, 고개 움직임의 안정성, 사용자 보정 부담으로 나누어 평가한다. “자연스럽다”는 평가만 남기지 않고 문제 부위와 재현 조건을 기록한다. 평가 점수 기준과 표본 수는 기술 검증 단계에서 확정한다.

02단계에서 [검증 입력 29건·장비 후보·격리 실행 환경](./planning/02-readiness.md), [공식 후보 조사](./planning/02-candidates.md), [0~3점 탐색 척도·성능 기록·재현 절차](./planning/02-evaluation.md)를 마련했다. 출시 합격 점수·표본·성능 임계값은 DEC-11에서 후속 확정한다. 현재 준비 검사의 예상 결과 일치는 자동 인식·리깅·방송·외부 구동의 성공률이 아니다.

03단계의 [실제 시제품·표본 검증](./planning/03-feasibility.md)에서는 세 경로를 같은 구조·눈/입/평면 고개 제어로 연결하고 저장·재열기·보정을 확인했다. 기술 검사 69개·Tk 위젯 통합 검사 17개는 통과했으며, 한 장 입력 18건은 성공 7·일부 실패 7·실패 4로 구분했다. 고급 원화의 동적 표현·가닥 경계, 가림 보완, 잘림·화풍 일반화, 초보자 관찰은 여전히 미완료다. 실제 CPU 프레임 생성 시간은 약 0.54~0.60초로, 30 FPS·추적·방송 성능 통과 증거가 아니다. 직접 OS 마우스 검수는 제어 도구 연결 불가로 미수행했고 위젯 검사는 프로세스 내 검사임을 구분했다.

04단계 [실제 외부 사용 검증](./planning/04-tracking-broadcast-export.md)에서는 사용자 입력과 장치 해제/복귀, 실제 OBS Browser Source 투명 합성·부하, 고급 원화/표정의 내장 INP·공식 Session 독립 재생을 확인했다. 기본 데모를 도형에서 고급 자산으로 교체하고 알파 변환 결함을 수정했다. 고급 캐릭터의 실제 640px 카메라+OBS 갱신은 약 13.57FPS로 30FPS에 미달한다. 마이크 RMS의 음성/소음 구분·고급 동적 표현·자동 리깅·외부 라이브 장치 연결·장시간 송출은 제품 합격으로 처리하지 않는다.

### 20.3 장기 기능의 별도 완료 기준

- 3D: 입체 구조를 확인·보정하고, 추적 실행과 방송 출력 및 선정한 외부 3D 대상에서의 구동까지 검증한다.
- 자체 모델 생성: 자체 모델의 정의와 제작 범위를 충족하고, 설명 입력부터 결과 선택·수정·공통 제작 흐름 연결까지 검증한다.
- 장기 기능은 별도 화면에 결과가 표시되는 것만으로 완료 처리하지 않는다. 실제 사용 경로까지 이어지는지 확인한다.

## 21. 성공 지표와 측정 계획

### 21.1 핵심 성과 지표

**주요 지표 제안: 신규 사용자가 캐릭터를 제작해 실제 방송 프로그램에서 사용 확인까지 도달하는 비율.**

| 첫 움직임 도달률 | 제작 시작 프로젝트 중 움직임 미리보기를 확인한 비율 | 자동 준비와 보정 흐름 평가 |
| 방송 연결 완료율 | 제작 시작 사용자 중 정해진 관찰 기간 안에 외부 방송 화면 확인을 마친 비율 | 실제 사용까지의 완결성 평가 |
| 첫 사용 소요 시간 | 제작 시작부터 첫 움직임 / 첫 방송 확인까지의 시간 | 초보자 부담 확인 |
| 자동 처리 후 보정량 | 수정한 부위 수, 보정 단계 수, 사용자 작업 시간 | 자동화의 실질 효과 확인 |
| 내보내기 성공률 | 내보내기 시도 중 파일 생성 성공 비율과 외부 구동 확인 비율을 별도 측정 | 변환 완료와 실제 호환 구분 |
| 저장·복구 안정성 | 실패·손상·복구 결과와 재현 조건 | 데이터 보호 확인 |
| 반복 사용 | 정한 기간 안에 같은 프로젝트로 다시 실행·수정한 비율 | 일회성 체험을 넘어선 활용 확인 |

01단계의 [측정 정의](./planning/01-metrics.md) v0.1에서 지표별 분모, 시작·종료, 첫 사용 7일·반복 사용 14일 관찰창, 설치·대기·능동 시간, 실패·도움·미확인 처리 규칙을 고정했다. 이는 최초 측정의 운영 기준이며 성능·성공률 약속이 아니다. 목표 비율과 출시 검증 표본은 DEC-11/T-047에서 후속 확정한다. 정성 조사 모집 목표와 출시 검증 표본을 구분한다. 연구 참여자의 완료·중도 이탈을 함께 기록하고 개발자가 대신 조작한 경우를 별도 구분한다.

### 21.2 측정 방법과 개인정보

초기에는 동의받은 사용성 테스트와 로컬 진단 기록으로도 측정할 수 있다. 제품 분석 서버나 계정 시스템을 선행 필수로 두지 않는다. 외부 방송 화면을 자동 확인할 수 없는 경우 사용자 확인값 또는 관찰 결과임을 표시한다. 텔레메트리를 도입한다면 수집 항목과 동의를 별도 설계한다.

## 22. 단계별 개발 계획 제안

기간과 인원은 아직 확정하지 않는다. 아래 순서는 위험을 조기에 검증하기 위한 제안이며 초기 제품의 필수 범위를 삭제하는 계획이 아니다. 특히 **외부 내보내기는 마지막에 가능성을 확인할 기능이 아니라 초기 구조 검증 대상**이다.

M5-A와 M5-B의 선후 또는 병행 여부는 팀 규모와 연구 결과를 보고 결정한다. M0~M3에서도 방송·내보내기의 작은 검증을 반복해 내부 편집 구조와 외부 사용이 어긋나는 것을 막는다.

**2026-11-16 M0 검토:** 05의 결정/검토 작업은 완료했으나 M0는 **HOLD**다. 실제 성능 미달·고급 자동 제작/파츠·초보자·외부 표현/활용·새 스택 포장/통합을 [M0-R01~05](./planning/05-m0-review.md)에 반환했다. 이 항목을 해결하는 격리 실험/최소 기반 작업과 M1 제품 기능 진행을 구분한다. 전체 06 이후 Todo나 출시를 자동 완료/승인하지 않는다.

### 22.1 초기 2D 출시의 최소 완결 단위

1. 파츠 조합, 한 장 그림, 분리 그림을 각각 공개한 지원 범위 안에서 처리한다.
2. 외형을 만들고 기본 표정·입·고개 반응을 설정한다.
3. 자동 인식이 틀린 부분을 쉬운 안내로 보정한다.
4. 카메라·마이크 입력을 연결하고 앱 내에서 실행한다.
5. 실제 방송 프로그램에서 캐릭터를 확인한다.
6. 최소 하나의 검증된 외부 아바타 대상에 내보내고 구동한다.
7. 이미지 저장과 프로젝트 저장·재개·복구를 제공한다.

중간 시제품은 이 중 일부만 포함할 수 있다. 하지만 일부만 구현된 시제품을 전체 초기 요구사항을 충족한 제품으로 표현하지 않는다.

### 24.1 06단계 개발 기반 구현 상태

[06 완료 기록](./planning/06-foundation.md)에서 T-051~060을 확인했다. 실제 제품 앱 골격과 고급 미리보기, 공통 모듈/포트·제한된 IPC·로그·프로필·고정 의존·자동 검사·포터블 EXE/ZIP을 만들었다. 새 폴더의 Node/venv/npm 설치에서 필수 11개 검사 그룹과 실제 앱 smoke를 통과했다. 별도 PC/VM이 없다는 사용자 답변에 따라 동일 PC의 개발 도구 PATH 제거·새 프로필·한글/공백 경로에서 배포본을 두 번 실행했다. 새 Windows 합격으로 해석하지 않는다. 호스팅 CI는 구성만 완료하고 실행하지 않았다.

이는 제품 개발 기반의 완료이며 세 제작 경로·프로젝트 저장/복구·실시간 추적·OBS 전달·제품 exporter의 완료가 아니다. 현재 renderer는 고급 샘플의 표정 패치와 제한된 평면 동작만 표시한다. 새 OS/오프라인·실제 제품 통합·성능·자동 제작·초보자·외부 의미 보존은 M0-R01~05 OPEN이다. M0 HOLD와 52개 기능·12개 PD·15개 AC 및 필수 장기 범위를 유지한다. T-061 이후는 미완료다.

### 24.2 07단계 공통 모델 구현 상태

[07 완료 기록](./planning/07-common-model.md)에서 T-061~070을 확인했다. `Project` 1.0에 표시 이름과 독립된 ID, 세 입력 경로, UTC 시각·현재/저장 리비전, 원본/파생 DAG, 부위/그룹/계층, 매개변수·상태/변환·입력 연결, 표정·실행/방송/내보내기 프로필을 구현했다. 기기 식별자와 보정은 프로젝트 밖에 둔다. 원본·편집·로컬·프로젝트·화면·출력 변환과 실제 파일 해시/이동/재연결·버전/참조 검사를 제공한다.

세 경로의 기존 준비 결과를 같은 구조로 구성했고 고급 기본 화면도 공통 모델을 읽는다. 기존 포함 25개 검사 그룹, 400개 affine 왕복, 실제 GPU 이동/crop과 동일 PC release 2회 실행을 확인했다. 제작/재연결 UI·ZIP 안전 저장·비동기 작업 제어는 T-071 이후다. 모델의 프로필이 실제 추적/방송/외부 구동 구현을 의미하지 않는다. M0 HOLD·5개 OPEN과 필수 범위/수용 기준은 유지한다.

### 24.3 08단계 작업/편집 제어 구현 상태

[08 완료 기록](./planning/08-async-workflow.md)에서 T-071~080을 확인했다. 독립 상태 축과 요청 시점 불변 입력, 작업/프로토콜/처리 버전, 큐·진행·취소/정리·실패 단계 재시도, 원자적 변경 단위와 리비전 CAS를 구현했다. 같은 프로젝트의 오래된 준비 결과는 AWAITING_REVIEW로 보류하고 현재 보정과 비교·선택 적용/재검증·폐기·최신 입력 재실행을 제공한다. 기존 stale 폐기 정책을 이 요구에 맞게 상세화했으며 다른 프로젝트/세대·취소/중복 응답 차단은 유지한다.

변경별 의존 결과를 stale로 표시하고 필요한 검사만 재실행하며, 편집/작업 실패와 정상 실행 스냅샷을 분리한다. 고정 입력·모의 작업과 실제 자식 프로세스/소유 임시 파일, 앱의 상태 UI를 포함해 기존 포함 45개 검사 그룹을 확인했다. 저장/내보내기 receipt는 상태 시험이며 실제 파일 저장 성공이 아니다. 실제 분석/저장/출력 통합은 T-268, 저장 공간/권한/경로 실패는 T-271에서 다시 검증한다. T-081 이후와 M0 HOLD·5개 OPEN을 유지한다.
